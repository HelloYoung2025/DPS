# Command Orchestrator migrations

`001_create_command_orchestrator.sql` is the proposed PostgreSQL 18.4 baseline. It creates append-only command, lease, attempt-event, signed-receipt, outbox, quarantine, migration-ledger, and catalog-attestation records. Command state is projected from immutable attempt events using attempt and explicit transition order rather than trusting identity-sequence direction; no state row is rewritten. Lease, binding, dispatch validity, and recovery timestamps come from the database clock after the per-command lock. Startup attestation covers the exact object inventory and ACL allowlist plus every identity sequence's type, start, increment, min/max, cache, cycle, identity mode and owned-by dependency.

The migrator owns the schema, tables, sequences, triggers, and `SECURITY DEFINER` functions. The runtime login receives only schema `USAGE` and `EXECUTE` on the exact versioned API inventory. It receives no direct table, column, sequence, DDL, ownership, inheritance, or PUBLIC-derived privilege. Each runtime API verifies a separate 256-bit process capability before reading or mutating module data; only its SHA-256 is stored in the append-only migration ledger. Startup binds the embedded migration SHA-256, capability SHA-256, exact PostgreSQL version `180004`, roles, owners, ACLs, function bodies/configuration, tables, columns, constraints, indexes, and append-only triggers into a catalog attestation. Any drift fails before runtime work.

Migration changes must be additive and receive a new immutable ledger entry; never rewrite this baseline or disable its append-only triggers in production. The required 21-test real PostgreSQL suite must pass before `INTEGRATION_VERIFIED` can be claimed.

The fixed cold bootstrap installs immutable `001_create_command_orchestrator.sql` followed by `002_restrict_default_function_privileges.sql` in one serializable transaction, only when the module schema is empty and has no ledger. Migration 002 preserves the v1 ledger row and appends v2, evolves the ledger constraint to versions 1/2 and the catalog-attestation constraint to version 2, and retains the runtime functions' signatures, security attributes, ownership, and ACLs. Startup requires exactly those two ledger rows with the separate SHA-256 of each embedded migration, the same capability digest and migrator, and PostgreSQL 18.4. The single final catalog attestation and runtime attestation use v2 and the 002 SHA-256; that SHA is not a combined migration digest.

Migration 002 removes the current restricted migrator's global default PUBLIC function EXECUTE in the current dedicated database. This tightens permissions on that role's future functions across schemas; it grants no additional runtime privilege, changes no existing object ACL, and does not affect another database or role or cancel a separate per-schema grant. The dedicated database and separate restricted role requirements remain mandatory.

Existing ledgers are verified only. A v1-only, unknown, incomplete, or altered ledger is rejected without upgrading, rewriting history, cleaning ACLs, or recreating attestation. Restoring default PUBLIC EXECUTE after installation is drift and must be rejected, never repaired during restart. This release supports fresh rollout only; existing-database upgrades require a separate reviewed migration. Failures before transaction commit roll back installation. Runtime connection attestation occurs after commit, so its failure can leave the complete v2 installation persisted while the service remains uninitialized. No down migration is supplied.
