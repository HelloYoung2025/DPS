# soul-registry operations

The module is proposed and not production release eligible. Runtime routing may change only through an exact signed Release BOM.

## Receipt hashing across alias-key rotation

The P05 implementation slice separates alias lookup from idempotency verification. Alias lookup uses the active lookup keyring. New resolution and mutation receipts record hash version 2 and exactly one hash key ID, with the operation and complete request commitment under separate versioned hash domains. Replay uses that recorded key, including after a newer lookup key becomes current. Retain the recorded verification key for the required replay period; reusing a key ID with different key bytes must fail verification.

Legacy version 1 receipts keep their original hashes and result bytes. When their hash key basis is absent, the service may verify the exact current key set or an explicitly configured historical key set in `LegacyReceiptHashKeySets`. Each historical set must name the complete known original key IDs, with the corresponding key material retained. Only an exact match to the complete stored legacy request hash permits replay. The result alias key alone is not the request hash basis; subset guessing and rewriting an old receipt are forbidden. Missing, ambiguous or unverifiable history fails closed.

Apply the additive receipt-metadata migration before enabling the new binary. The original receipt fields and append-only protections remain. Older writers still create version 1 receipts with no basis metadata. However, the old binary cannot replay a new version 2 receipt, even with the same single key. Stop old writers before enabling version 2 writes. Once version 2 receipts exist, rollback requires a binary that understands them or a forward fix; do not drop the metadata or rewrite stored hashes and results. Retaining the old binary as a rollback target requires a separately validated compatibility stage, which this slice does not implement.

Runtime identity verification, Soul current-resolution authority, Binding composition and the positive Ledger v2 integration remain separate P05/P11 work; this hash repair does not make caller-supplied verification flags authoritative.

An internal test-composed core now verifies an evidence provider's exact request commitment, signs and validates the owner alias proof, records nonce and complete retained-key references, and atomically applies create/attach/resolve/revoke to separate authenticated alias rows. It checks old alias rows for conflicts without promoting them. ## Proposed local Soul-current read composition

`ControlPlaneSoulCurrentComposition.Open()` is a callable product API. `Program.cs` and `--self-check` are unchanged and no production traffic/listener is registered. Both modules remain release-ineligible; all four identity contracts stay quarantine-only. This is an explicit Proposed composition-only Host -> Soul runtime factory dependency exception, with the reader using contracts only. Earlier absent-composition statements above describe the prior slices.

Production root is fixed at `/Library/Application Support/DPS/soul-current`; bootstrap/configuration/composition/current-state files are strictly parsed and reread on acquire and final validation. Root approval binds exact configuration/BOM/generation and loaded artifacts; it is not revocation authority. Actual Default-ALC Host/Soul/contracts assembly locations, unique identities, PE identity/MVID and same-protected-file hashes must match the protected generation prepared before process start. Dynamic assemblies, shadow copies, other ALCs, writable replacements and late changed artifacts reject. This assumes a trusted CLR/OS/root and does not defend an already compromised root or process.

Descriptor-relative O_NOFOLLOW traversal holds and revalidates the protected directory chain. Each actual file/directory read uses same-fd owner/type/mode/fstat/ACL checks. Nonempty ACLs reject. Only immediate acl_get_fd_np NULL/ENOENT can fall back to complete same-held-fd fgetattrlist proof of an extended-security-capable same mount and strictly parsed empty ACL, with matching identity/times; unknown/error/contradiction never becomes success by retry. Sockets use the validated parent's fd and fixed basename, complete same-mount capability proof and strict Darwin four-byte-packed getattrlistat metadata/ACL parsing before/after connect, plus actual getpeereid and typed signatures. Equal metadata does not prove no ABA, and peer credentials do not bind a socket pathname vnode; protection relies on untrusted processes being unable to replace the parent chain. Other OS or unsupported native protection fails closed. Actual production hierarchy, service provisioning and cross-UID isolation remain unverified; default macOS path aliases/permissions are not assumed safe.

Three distinct roles are required: Host/provider with no signing keys, dedicated host-auth signer with only the possession key, and dedicated current signer with distinct current/status keys. Fixed sockets are `/var/run/dps-soul-current/host-auth/service.sock` and `.../current/service.sock`. Key IDs select fixed service-private protected slots; public callers cannot select roots, paths or keys. Each product handler authenticates the peer and exact tenant/Soul/principal/permission. Current state is freshly read from protected authority-state.v1.json for every status/sign RPC, with monotonic revision/epoch and nonce/query/session/BOM bindings. Static bootstrap approval cannot renew revoked authority.

Provider and signer use distinct NOINHERIT, nonmember, nonsuperuser SELECT-only database logins and separate protected secret IDs. The signer reads a REPEATABLE READ READ ONLY owner/active-alias snapshot, selects deterministically with C collation and signs only its own facts; it never accepts caller revision/alias/status fields. It does not contend for the provider's held exclusive advisory lock. Provider compares every returned owner/alias fact and revalidates actual session lock, owner state and fresh authority status before success. Cancellation/deadline/disconnect discards late signatures, drains local operations and disposes the nonpooled lease; this makes no assertion that remote work stopped.

Synthetic tests prepare owned temporary installation generations, use two separate signer PIDs retaining generated keys, and launch a child Host that loads those exact artifacts through the same product factory/handlers. The internal test seam substitutes only owned paths/UID/material; same-UID process separation plus real cryptography/PG is lower-strength evidence than protected production isolation. No production files, users, launch services or keys are installed. Missing production root/service/key remains AUTHORITY_UNAVAILABLE.

Stop by keeping routing unregistered and disabling the protected bootstrap or revoking current authority state through its external owner. Rollback selects a separately approved compatible generation/BOM and restarts its processes; old in-flight leases cannot be renewed by static approval. This unit adds no migrations, business writes, privacy stores, retention policy, production activation or formal evidence issuance. The retained P11 Soul-to-Ledger failure and global gate blockers remain separate unfinished obligations; no P05 package/P06/P11 readiness or Windows/device claim is made.
