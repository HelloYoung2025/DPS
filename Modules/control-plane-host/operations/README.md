# Control Plane Host operations

Policy Approval uniquely owns the strict reconciliation, recovery, and signed submission-state contracts. Control Plane Host uses only that public contract pack. Reconciliation and human recovery signing are separate, strongly typed asynchronous external capabilities with different canonical P-256 identities; the recovery authority receives the complete bounded recovery DTO before it can authorize a signature, and the host never accepts raw lifecycle private-key material. Authority calls and Policy port calls each have a hard maximum five-second timeout and recheck cancellation before and after every external boundary. A timed-out or indeterminately cancelled authority is quarantined: no second call may start, its private payload copy remains intact until the uncooperative task finishes, and any late signature plus payload are then zeroed without emitting a wire. This is fail-closed containment, not proof that a remote authority stopped processing; a production authority must use an abortable authenticated process boundary and idempotent approval receipt.

The current `in-process-api` ports are proposed role-specific contract facades only. Distinct objects, exact auth-scope declarations, different credential-authority fingerprints, and bounded calls are local fail-closed configuration checks; they are not evidence of peer authentication, process isolation, credential isolation, or production composition. Production must replace these facades with authenticated role-specific IPC/RPC adapters whose independent credentials remain outside the Control host; those adapters must derive peer identity and authorization from the actual mTLS, OS-protected IPC, or equivalent Policy/database-role session rather than trusting the interface's self-reported strings. A Policy-state response is accepted only after strict codec, commitment, signature, exact identity/scope/idempotency, Release BOM, intent/native binding, predecessor, and evidence verification. Unknown, empty, timed-out, forged, or mismatched responses leave the old attempt blocked.

No production lifecycle composition is installed by `--self-check`. Activation remains R3, human-approved, exact-BOM-bound, and fail-closed until the independent reconciler, human approval broker with auditable approval receipts, Policy-state trust key, authenticated role-specific Policy IPC/RPC adapters, real PostgreSQL 18.4 integration, canary, kill switch, and rollback evidence exist. Rollback stops new lifecycle issuance; it never reopens or rewrites an old attempt.

The host is proposed and has no production listener. `--self-check` is the only accepted local startup mode. PostgreSQL migrations require an explicit non-runtime migration login and a dedicated Control Plane database target. Runtime uses a distinct, login-capable, non-member role with schema usage, `SELECT` only on the five module tables, and `EXECUTE` only on the exact JSON helper plus the two fixed atomic commit/quarantine functions. Runtime has no direct table `INSERT`, mutation, DDL, database `TEMP`, role inheritance, or migration role. Both paths enforce five-second connection, command, statement, lock, and idle-transaction limits, exact PostgreSQL 18.4, origin trigger execution, and rejection of GBrain Company's port/database.

`policy-approval` uniquely owns the strict `action.execution.promotion/v1` input contract; this module consumes its public contract pack and is the only allowed wire producer. A shadow proposal never authorizes execution. Production promotion issuance is not implemented in this slice: it remains fail-closed until an independently verified release-approval source and secret-backed P-256 signer are implemented, tested, and human-approved. The policy-owned codec fixes the exact bounded wire and canonical signature bytes so neither side can accept a loose substitute.

Every new or equivocal ingest starts from bounded strict UTF-8 raw v1 JSON bytes. The host rejects duplicate/additional fields and non-canonical identifiers, resolves the latest provider trust revision, requires its active release BOM and canonical NIST P-256 key, verifies the P1363 signature, and stores the exact raw bytes, digest, trust revision, public-key digest, signature, and authorization digest. An exact immutable redelivery whose raw bytes, BOM, key ID, signature, authorization digest, and committed record all match returns the existing receipt even after later key revocation; it creates no new truth, receipt, outbox, or quarantine row. One owner-controlled database function commits truth, receipt, and outbox in a single transaction; a second function appends only hash-scoped conflict quarantine. Startup attests the exact five-table/83-column/89-constraint catalog and persisted PG18.4 definition comments, 13 trigger tuples, three independent indexes, eight function bodies and security modes, isolated role graph, built-in `pg_catalog."C"` collation, object ownership, and ACLs before every operation.

For `soul.memory.readback/v1`, this host verifies the signed SoulMemory adapter proof and exact equality of its declared projection and read-back checksums. The source contract does not carry the original GBrain content, so the host does not claim that it locally recomputes a checksum from GBrain bytes.

Shadow truth comparison must precede a human-approved bounded canary. The kill switch stops ingest; rollback retains runtime truth, receipts, quarantine, and outbox rows and restores the previous signed BOM. Rollback never rewrites or truncates the journal.

Personal-data export, correction, retention enforcement, and verified erasure are not implemented in this slice. The append-only tables retain canonical scope identifiers and exact signed provider JSON bytes; this module therefore remains `releaseEligible: false` until an independently approved retention and cryptographic-erasure or equivalent audited design is executable and tested.

## Quarantined four-role Soul-current read

Public Host/provider/signer Open methods always reject. Both modules remain release-ineligible and identity/session contracts remain quarantine-only. There is no Host→Soul runtime factory exception, production route, or activation through `enabled=true`. Fixed internal test-only entry assemblies exercise the real handlers.

Production root is fixed at `/Library/Application Support/DPS/soul-current`; bootstrap/configuration-v2/composition/current-state files are strictly parsed and reread on acquire and final validation. Root approval binds exact configuration/BOM/generation and loaded artifacts; it is not revocation authority. Host verifies its actual Host/contracts assemblies; provider and each signer verify their actual Soul/contracts assemblies. Default-ALC assembly locations, unique identities, PE identity/MVID and same-protected-file hashes must match the protected generation prepared before process start. Dynamic assemblies, shadow copies, other ALCs, writable replacements and late changed artifacts reject. This assumes a trusted CLR/OS/root and does not defend an already compromised root or process.

Descriptor-relative O_NOFOLLOW traversal holds and revalidates the protected directory chain. Each actual file/directory read uses same-fd owner/type/mode/fstat/ACL checks. Nonempty ACLs reject. Only immediate acl_get_fd_np NULL/ENOENT can fall back to complete same-held-fd fgetattrlist proof of an extended-security-capable same mount and strictly parsed empty ACL, with matching identity/times; unknown/error/contradiction never becomes success by retry. Sockets use the validated parent's fd and fixed basename, complete same-mount capability proof and strict Darwin four-byte-packed getattrlistat metadata/ACL parsing before/after connect, plus actual getpeereid and typed signatures. Equal metadata does not prove no ABA, and peer credentials do not bind a socket pathname vnode; protection relies on untrusted processes being unable to replace the parent chain. Other OS or unsupported native protection fails closed. Actual production hierarchy, service provisioning and cross-UID isolation remain unverified; default macOS path aliases/permissions are not assumed safe.

Four distinct roles are required: Host holds neither Soul runtime nor Soul PG credentials/private keys; provider holds only its SELECT-only DB credential/owner lease; host-auth signer holds the possession key; current signer holds distinct current/status keys and its independent SELECT-only credential. Production configuration requires four distinct UIDs. Fixed socket basenames are `provider/service.sock`, `host-auth/service.sock`, `current/service.sock` under `/var/run/dps-soul-current`. Provider and host-auth accept only the actual Host peer; current signer accepts only provider. Configuration v2 preserves all former key, role, secret, database and deadline guards. Static bootstrap cannot renew revoked authority; status/sign operations reread protected authority state and validate actual loaded artifacts.

Provider and signer use distinct NOINHERIT, nonmember, nonsuperuser SELECT-only database logins and separate protected secret IDs. The signer reads a REPEATABLE READ READ ONLY owner/active-alias snapshot, selects deterministically with C collation and signs only its own facts; it never accepts caller revision/alias/status fields. It does not contend for the provider's held exclusive advisory lock. Provider compares every returned owner/alias fact and revalidates actual session lock, owner state and fresh authority status before success. Cancellation/deadline/disconnect discards late signatures, drains local operations and disposes the nonpooled lease; this makes no assertion that remote work stopped.

Synthetic tests prepare owned temporary installation generations, merge both launcher outputs into one generation before any child starts, rejecting unequal shared DLL bytes, then run provider/two signers and an independent Host child that proves no Soul runtime is loaded. Signer keys never leave their respective children. The internal test seam substitutes only owned paths/UID/material; same-UID process separation plus real cryptography/PG is lower-strength evidence than protected production isolation. No production files, users, launch services or keys are installed. Missing production root/service/key remains AUTHORITY_UNAVAILABLE.

Stop by keeping routing unregistered and disabling the protected bootstrap or revoking current authority state through its external owner. Rollback selects a separately approved compatible generation/BOM and restarts its processes; old in-flight leases cannot be renewed by static approval. This unit adds no migrations, business writes, privacy stores, retention policy, production activation or formal evidence issuance. The retained P11 Soul-to-Ledger failure and global gate blockers remain separate unfinished obligations; no P05 package/P06/P11 readiness or Windows/device claim is made.

Normal release requires explicit owner-backend unlock=true, absence of the exact advisory lock and completed connection close before ACK. Host checks the original 5000ms budget, caller cancellation and signed windows again after ACK. Fault cleanup waits at most 5000ms separately, with bounded driver cancellation and observed late cleanup; it neither retries authority nor proves uncontrolled work stopped. Keep closed routing/kill switches effective. A rollback requires a separately approved compatible generation/BOM; do not reactivate the deleted v1 runtime factory or rewrite R1/R2 evidence.
