# Policy Approval tests

The 0.6.0 ownership tests assert that Policy Approval product and contract assemblies publish no `native.stop.*` DTO or embedded resource, its contract project packs no native-stop Schema/Corpus, production factories expose no caller-selected trust, and `SubmitNativeOnceAsync` accepts only cancellation. The single public native-dispatch Integration case must return `WAITING_EXTERNAL` and create zero PENDING rows. Native result truth remains `CONFIRMED_SUCCESS`, `FAILED`, or `UNKNOWN_OUTCOME`; transport acknowledgement is not success.

Unit and Contract suites cover strict opaque identifiers, strict canonical commitments, delimiter-collision resistance, invalid UTF-8, deterministic deny/approve rules, immutable proposal snapshots, independent promotion signer separation and exact binding, signature and role attacks, unknown policies, exact scope, kill switch, rate budget, platform authorization, two-second execution-fence DTOs, non-constructible authoritative snapshots, and the policy-owned native-submission lifecycle. Decision, evaluation request, promotion, fence, intent, acknowledgement, reconciliation, recovery, and state owner corpora are checked by Draft 2020-12 schema tests and by their C# DTO validation, including unknown, missing, duplicate, UUID, canonical-time, year-zero, Int64, digest, signature, authority, lifetime, predecessor, evidence, Release BOM generation, and cross-field rejection cases. Both gates lock the exact expected case ID sets, counts, and uniqueness so removing an adversarial case is a failure.

The 0.7.0 proposal-major tests run the Planner owner `action.proposal/v2` corpus through the Policy entry gate; the corpus is linked read-only and its SHA-256 must equal the owner schema's `x-dps-adversarial-corpus-sha256`. Valid v1 wire is quarantined with a bounded hash-only proof, unknown majors and malformed contract IDs fail closed, the API-shape test fails if a v1 typed evaluation entry or the removed envelope types return, and a contract test pins migration 005 as registered, embedded, expand-only, and grant-free.

The composition API-shape tests reflect the public clients and options. They fail if executor regains reconciliation/recovery methods, if reconciler/recovery gains acquire/begin/acknowledgement methods, if one options record regains another PostgreSQL credential, or if any of the eight evaluation/promotion/revocation/fence/executor/reconciliation/recovery/state authority fingerprints collide. Credential `ToString()` output must remain redacted.

The required Integration suite uses only a real PostgreSQL 18.4 instance supplied through `DPS_TEST_POSTGRES`. It covers concurrent same-request idempotency, a one-connection pool proof for transaction-bound state reads, atomic one-unit rate-budget competition, different-hash quarantine, transaction crash windows, restart readback, exact cross-Soul/device/account isolation, independently signed promotion and signed revocation, stale revisions, final database-clock revalidation, execution-fence lock serialization, status-reason and exact outbox-to-receipt constraints, prompt-injection-shaped parameters, kill switch/rate/platform authorization, revoked runtime state, exact least-privilege runtime-role identity/attributes, and owner-level append-only triggers.

The proposal-major Integration cases prove the v2 `EXECUTE` plus promotion approval without any submission row, v2 `SHADOW` denial with zero rate and lifecycle rows and a refused fence, v1 and unknown-major rejection with zero rows, request binding before any write, signature-free replay versus business-field conflicts, zero writes for an expired new request while an issued request still replays, migration 005 over historical v1 rows including revocation and idempotent re-initialization, the attempt trigger for every caller including the owner, and v1 isolation at the duplicate receipt branch, reader, and fence through the one shared snapshot guard.

The lifecycle portion proves three separate native-submission crash windows: pending committed before any native call, native submission flushed before acknowledgement commit, and acknowledgement validated before the policy transition commits. It also proves that an exact duplicate begin is readback-only, pending survives restart and blocks redelivery, a second acquire waits behind the shared command lock and then rejects committed pending, concurrent acknowledgement/reconciliation commits exactly one terminal branch, lock waits cannot extend a fence or receipt, a durable acknowledgement is terminal, cross-scope/forged reconciliation and recovery reuse fail, and only `CONFIRMED_NOT_SUBMITTED` plus a distinct human recovery authority can bind the next attempt.

The former eight label-only missing-authority callback cases are deleted and are not accepted as Integration evidence. `004_create_native_stop_challenge_ledger.sql` is not a product migration: the product assembly cannot embed it and the product migrator cannot discover it. `ProposedNativeStopDesignHasRealPostgresCatalogAclAndMutationGuards` is labelled `Category=ProposedDesign`, is excluded from the product Integration suite and its evidence count, and exists only for future design review. It first proves product initialization left both tables absent, then explicitly installs the SQL from the test artifact only. It inspects both design tables, all four UPDATE/DELETE/TRUNCATE triggers, and all three function ACLs. For both tables it requires catalog-level denial of `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER` to `PUBLIC`, generic runtime, executor, reconciler, and recovery; every login role must also receive a real `42501` for `SELECT`, `INSERT`, `UPDATE`, `DELETE`, and `TRUNCATE`. It seeds both tables as the owner and proves UPDATE, DELETE, and TRUNCATE are rejected by the append-only triggers. Missing or unreachable PostgreSQL is `INFRA_ERROR`, never a skip or Mock success. Passing this proposed-design check cannot activate the migration, become product `INTEGRATION_VERIFIED` evidence, or satisfy current release eligibility.

That negative case requires real PostgreSQL owner setup and cannot be replaced by a Mock.

The database gate creates pairwise-distinct generic-runtime, executor, reconciler, and recovery login roles. It proves disjoint security-definer grants, no role membership or direct table mutation, exact JSON field sets, missing/unknown-field RPC rejection, removal of the legacy five-argument begin overload and generic helper, and unknown-overload detection. Missing PostgreSQL is `INFRA_ERROR`, never a skip or Mock success; the suite refuses port `55434` and `dps_gbrain_company`.
