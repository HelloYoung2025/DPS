# Policy Approval contracts

## Existing execution-authorization assets

Policy.Contracts uniquely defines `execution.authorization/v1`, its existing payload guard and `ExecutionAuthorizationCanonicalV1`, and packages/embeds its [schema](provided/execution.authorization.v1.schema.json) and [machine canonical specification](provided/execution.authorization.v1.canonical.json). Those two JSON assets retain their original bytes and all existing v1 validation/canonical semantics. The DTO retains the historical `Dps.CommandOrchestrator.Contracts` namespace for source compatibility; the compiled definition belongs only to Policy.Contracts. Old binary compatibility is not claimed. Command.Contracts references Policy.Contracts and forwards authorization canonical calls; Policy references neither Command nor Compiler. Command still owns dispatch, its digest and leases, and remains the wire producer.

Policy declares the same active major as both provider and receiver consumer for the existing Command request/return boundary. The signed return preserves the Command producer. These declarations do not implement a signer: the old Command consumer `SignAsync(ExecutionAuthorizationV1)` port remains. Typed requests, strict codecs/corpora, durable provenance, authoritative signing and authenticated Host composition remain separate P04/P08 work. Existing fail-closed runtime, quarantine and release-ineligible status are unchanged.

## Native execution ownership boundary (0.6.0)

Policy Approval product and contract artifacts contain, compile, embed, and package no `native.stop.*` DTO, Schema, Corpus, codec, or verifier. Executor Gateway remains the unique owner of the registered native-stop contract. Policy may consume only an exact signed owner artifact after a future dependency/compatibility declaration and independent activation review; until then there is no Policy-local fallback contract source. The separate test artifact may copy the unregistered `004` SQL design and exercise its proposed parser only under `Category=ProposedDesign`; that code is absent from the product artifact and is not current contract, migration, or Integration evidence.

The public `SubmitNativeOnceAsync` method accepts no callback, signer, verifier, trust provider, or caller-supplied native proof. It returns `WAITING_EXTERNAL` before a PENDING insert while the exact signed Executor Gateway owner artifact, Release BOM/Supervisor/Worker authorities, and two-phase submitted-request commitment are unavailable. ACK is transport acknowledgement only; native result truth remains one of `CONFIRMED_SUCCESS`, `FAILED`, or `UNKNOWN_OUTCOME`, and ACK alone never establishes success. `approval.decision/v2` is intentionally absent rather than exposing a partial contract.

The module consumes `action.proposal/v2` from Planner; `action.proposal/v1` is quarantine-only. As the API provider it uniquely owns `approval.evaluation.request/v1`, `action.execution.promotion/v1`, `approval.decision/v1`, `approval.execution.fence/v1`, `approval.submission.intent/v1`, `approval.submission.acknowledgement/v1`, `approval.submission.reconciliation/v1`, `approval.submission.recovery/v1`, and `approval.submission.state/v1`. Contract ownership is intentionally centralized here even when Executor Gateway or Control Plane Host is the authenticated producer of an input envelope; consumers must not define a parallel policy-looking lifecycle DTO.

A `SHADOW` evaluation request always yields a shadow-only denial. A non-shadow approval requires an `EXECUTE` request plus an independent, exact-scope promotion signed by the Control Plane promotion authority. The promotion binds the v2 proposal commitment, runtime revision, database-time validity, Release BOM, and all Soul/device/account/trace/idempotency identifiers. Unknown fields, duplicate fields, non-canonical Base64, non-P-256 or non-P1363 signatures, stale revisions, expired windows, and scope mismatches fail closed.

## Evaluation request and proposal majors (0.7.0)

[`approval.evaluation.request/v1`](provided/approval.evaluation.request.v1.schema.json) is the signed Control Plane request that authorizes one evaluation. It binds the proposal ID and its v2 commitment, Soul/device/account/trace/idempotency, Release BOM, mode (`SHADOW` with a null promotion hash, or `EXECUTE` with the promotion's unsigned-payload hash), an `occurred_at` equal to the proposal's, and `valid_until = occurred_at + 120 s`. Its canonical domain is `dps.policy-approval.approval-evaluation-request/v1`. The P-256 P1363 signature is excluded from the commitment and stored in its own column: the signature is verified first, the signature-free commitment is the idempotency command hash, an identical re-signed request replays the original result, and a changed business field is a hash-only conflict.

From 0.7.0, `proposal_sha256` in `action.execution.promotion/v1` and `approval.submission.intent/v1` is always the v2 commitment (domain `dps.planner.action-proposal-sha256/v2`); v1 is never promoted. Their schema bytes are unchanged.

An approval is authorization evidence only; it is not an operation, command, native result, or proof of success. Fence revalidation is read-only. The segmented submission lifecycle remains internal/test-only for persistence and recovery compatibility. The public `SubmitNativeOnceAsync` production path is fail-closed `WAITING_EXTERNAL` in 0.6.0 and creates no PENDING fact until the owner-defined protocol is implemented and verified.

The lifecycle is append-only: `SUBMISSION_PENDING` is equivalent to `UNKNOWN_SUBMISSION` after any restart until an exact durable acknowledgement is accepted. Current production code cannot create that state through native dispatch. Internal persistence/recovery tests retain the no-retry rule: only a separately signed `CONFIRMED_NOT_SUBMITTED` reconciliation plus a distinct human recovery signature may authorize a fresh attempt.

Canonical lifecycle commitments are public through `ApprovalSubmissionLifecycleBinding`: `ComputeIntentSha256`, `ComputeAcknowledgementSha256`, `ComputeReconciliationSha256`, `ComputeRecoverySha256`, and `ComputeStateSha256`. They use strict UTF-8, domain separation, and unsigned-big-endian length-prefixed fields. `SUBMISSION_PENDING.EvidenceSha256` equals the intent commitment; acknowledged/reconciled/recovery state evidence equals the corresponding envelope commitment. Native request formation avoids a digest cycle: the base native binding excludes lifecycle proof, then the submitted request binds `submission_attempt_id + intent_sha256 + pending_state_sha256` under its separate submitted-request commitment.

Public decision and execution-fence JSON must pass the contract-pack codecs. They accept exactly one bounded strict-UTF-8 object with canonical snake_case field order, no unknown or duplicate fields, lowercase non-zero D UUIDs, non-zero-year canonical Zulu timestamps, and positive Int64 revisions. `approval.execution.fence/v1` uses the common `occurred_at` wire field and permits a positive lifetime of at most two seconds. PostgreSQL `jsonb` readback may change whitespace or object-key order, so the authoritative reader applies the same exact semantic field validation without pretending the database text is the original canonical wire; outbound JSON is always produced by the canonical codec.

Production eligibility remains false. A future active native path needs an owner-defined executor-authority-signed proof, an atomically consumed challenge row, an injected process-root guardian, exact reciprocal Executor Gateway/Supervisor/Release BOM contracts, independent secret brokers, real PostgreSQL evidence, and Windows process evidence. None is inferred from Policy Approval because this module publishes no native-stop contract.

`approval.readback/v1` (0.8.0) is the unsigned public projection of one authoritative approval snapshot, and the exact reader is its only producer. It embeds the exact `approval.decision/v1` payload. `approval_sha256` is the existing snapshot commitment, `proposal_sha256` and `proposal_contract_major` are the persisted proposal binding, and `request_signature` is the persisted migration-005 column: required for major 2, null for historical major 1. The top-level `soul_id`, `device_binding_id`, `platform_account_id`, `trace_id`, `idempotency_key` and `occurred_at` repeat the persisted scope of the same row and must equal the embedded decision. The readback commitment domain is `dps.policy-approval.approval-readback/v1`. A v1 readback can never be an ACTIVE non-shadow `APPROVED` decision, and a readback is never execution authority by itself. No migration was added.
