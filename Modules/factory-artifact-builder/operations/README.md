# Operations

Run in an isolated, module-owned POSIX output directory with declared inputs only. The runtime requires descriptor-relative `openat` support, `O_NOFOLLOW`, directory descriptors, file and directory `fsync`, and advisory output locking as available on the supported macOS/Linux service hosts. Repository and output path components must not be symbolic links; a path identity change aborts the build.

The hard resource envelope is 256 MiB per artifact/source file, 1 MiB per module manifest, 10,000 source files, 1 GiB total source bytes, 32 MiB of Git tree listing, and 64 MiB per generated JSON document. Raising a limit requires a reviewed capacity and denial-of-service analysis. A killed writer may leave only the deterministic hidden temporary name or a two-link fully written final; the next locked retry removes the temporary link and revalidates the final bytes before accepting it.

Compare the source digest before and after publication. The builder emits `UNSIGNED_AWAITING_EXTERNAL_SIGNER`; an external controlled signer validates and signs the later Release BOM. Files are staged, file-synced, linked without replacement, directory-synced, made non-writable, and re-read before return. These local controls do not provide WORM retention against an administrator or output-directory owner; production retention and deletion protection remain blocked on an external immutable artifact store policy. Shadow builds are never published. Rollback retains content-addressed artifacts and changes only BOM routing.

Before opening any output, validate the complete signed `merge.decision/v1` object, not only its signature. Its Soul, device, account, trace, integration commit, policy digest, approval outcome, and timestamp must bind to the build request, and the request cannot predate the decision. The requested module version must equal the version in the workspace Manifest after that Manifest is matched to the signed Git tree. A mismatch is a rejected build, never a corrected or normalized request.

Before publishing the first output byte, claim `build_id` through `factory_artifact.claim_build_identity(...)` in PostgreSQL 18.4. The claim binds canonical request and verified-decision digests plus artifact, source tree, module/version, and integration commit. The registry rejects autocommit, rolls back any borrowed transaction, forces `synchronous_commit=on`, requires `fsync=on` and `full_page_writes=on`, and commits the claim before publication. A lost acknowledgement fails the attempt; an exact retry is safe, while the same ID with any different bound value is rejected. Never substitute the in-memory unit registry in a service composition.

Apply migration `001_build_identity_claims.sql` only with a dedicated migration identity to a dedicated empty database. Use a different direct, non-inheriting runtime login, revoke database CREATE/TEMP from that role and PUBLIC in the dedicated database, grant it only `USAGE` on `factory_artifact` and `EXECUTE` on the nine-argument claim function, and grant no table, sequence, schema-create, or DDL privilege. Required integration evidence uses distinct admin/runtime URLs and exact PostgreSQL 18.4. Missing URLs, equal identities, a pre-existing schema, unavailable PostgreSQL, or unavailable locked driver is `INFRA_ERROR`, never a skip or local fallback.

The production registry rechecks this runtime boundary on every connection before calling the claim function: exact server version, `session_user == current_user`, direct login, `NOINHERIT`, no memberships, no superuser/role/database/replication/bypass-RLS flags, no database ownership/CREATE/TEMP, no schema CREATE, and exact schema/function/table/column ACLs. It also checks the migration attestation comments, common non-runtime owner, exact function bodies and settings, columns, every named constraint definition, the complete one-index set, and trigger wiring. Supplying a migrator, administrator, `SET ROLE`, drifted catalog, an extra index, a column grant, or a weak-durability connection is a rejected build, not a convenience fallback.

Artifact bytes keep their artifact digest name. SBOM, provenance, and descriptor each use the digest of their own canonical JSON bytes as the filename. Therefore two approved builds that produce identical artifact bytes but differ in source tree, merge decision, or build identity share only the payload file and retain separate metadata documents.

The outbound descriptor receipt derives `idempotency_key` from the durably claimed `build_id` with the `dps-artifact-descriptor-idempotency/v1` domain. An exact retry of one build keeps one receipt identity; two legal builds of identical artifact bytes have different receipt identities.

Build requests and emitted descriptors use one canonical UTC `Z` timestamp profile; RFC 3339 offsets are rejected rather than normalized. Module versions use the repository SemVer profile, including optional build metadata. The SPDX 2.3 JSON includes one mandatory SHA1 checksum per analyzed file solely for SPDX compatibility, keeps SHA-256 as DPS trust identity, computes the Package Verification Code from the exact listed file SHA1 values, and binds every listed file to the package with `CONTAINS`. The provenance document intentionally uses the DPS custom predicate `https://dps.local/provenance/module-artifact/v1`; it is not SLSA provenance evidence. Neither local metadata nor this proposed builder can self-authorize production publication.
